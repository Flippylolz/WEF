# 19 October 2026 catalog filter incident

Owner-directed, unplanned production incident: repair rolling-date filtering,
empty-result layout and calendar constraints, audit Telegram completeness, and
perform only supported bounded recovery. The owner explicitly authorized
implementation, safe operations, eligible merges and deployment verification in
the incident request. No new dependency, migration or publication-policy change
is part of this fix.

## Causes and changes

- Successful empty listing pages fell back to the last non-empty cards and count.
  Both desktop and mobile production reproduced 20 stale cards below the empty
  message. Empty successes now replace the saved snapshot, including its zero
  count. Failed requests retain the last successful snapshot, which may be empty.
- Selecting `last_day` cleared the manual lower bound but retained a manual upper
  bound. An old end date could precede the newly resolved cutoff and yield 422.
  Selecting a rolling preset now clears both manual date bounds in URL state.
- Date inputs used facet publication extrema as native `min`/`max`. Production
  facets ended at `2026-10-15T14:21:30Z`, making 19 October unavailable. Catalog
  extrema remain truthful data; they no longer restrict the date inputs.
- Result status blocks had no exterior spacing. Add block margins and predictable
  paragraph spacing; retain wrapping clear/reset buttons and existing touch sizes.

The backend still filters canonical `offers.published_at`, with an inclusive
cutoff of backend UTC now minus 24 elapsed hours. Source edits/ingestion times do
not make old publications new. Manual date-only URL bounds retain the established
UTC start/end-of-day conversion. Requests use `cache: no-store`; public responses
allow 30-second map/list and 60-second facet caching. Neither cache duration can
explain a four-day publication boundary. Production HTTP and database clocks both
reported 19 October correctly.

## Recovery and verification procedure

Use the [current offer backfill](OPERATOR_COMMANDS.md#current-offer-backfill-e28)
module, not a guessed console alias or a full archive reimport. A read-only canary
over `31745..31754` returned 9 non-candidates and 1 update candidate; no create
candidate. `update_candidate` does not imply changed canonical fields. Do not
apply an unrelated full page when no missing candidate was found.

Observe the source head again; enumerate explicit source IDs in batches no larger
than 100, honor Telegram flood waits, and reconcile present/deleted/unknown source
observations against raw and canonical presence. Keep source content and sessions
on the server. Store only IDs, aggregates and timestamps in public evidence.
For any confirmed missing candidate, dry-run its frozen bounded page, apply the
reviewed page through the existing command, repeat it, and compare canonical
identity/field/link counters plus continued live progress. Unknown or conflicting
address evidence requires the existing owner place-review flow.

Regressions cover empty success after non-empty data, error after empty success,
clear recovery, replacement of both manual date bounds, calendar dates past stale
facets, Warsaw midnight and DST, and SQL cutoff/count/pagination agreement.
Responsive browser tests exercise 320/390/1280-pixel views and clear/reset actions.

Rollback is the previous compatible application release through the existing
deployment workflow. No database schema or source deletion is introduced.
